## P1：已登记的 pixel_tolerance 模式接受全透明交付

本次使用未修改的 rev05 评估器和同一 p01 正常页面，生成三个独立交付 PNG：

1. 使用正常交付图片的 RGB 数据；
2. 编码成合法 RGBA PNG，所有 alpha 都设为 0；
3. 实际尺寸保持桌面 1280×900、移动端 390×844；
4. 复制原旁车，仅更新文件 SHA-256，其余相机和状态字段保持正确。

图片不可见，但隐藏 RGB 与正常截图相同。独立 Pillow 解码验证三张均为 RGBA，
alpha 极值均为 **[0, 0]**；不是错误尺寸或损坏文件。

| 实际交付 | 绑定模式 | 评估器结果 |
| --- | --- | --- |
| 正常图片 | 默认 byte_equal | PASS / exit 0 |
| 正常图片 | 显式 pixel_tolerance | PASS / exit 0 |
| 全透明图片 | 默认 byte_equal | FAIL / exit 1 |
| 同一组全透明图片 | 显式 pixel_tolerance | **PASS / exit 0** |

最终通过报告的三个像素比较均为零差异，但文件摘要与本轮截图不同。
原因：`png_decode.mjs` 的 `toRgb` 对 RGBA 只复制 RGB，忽略 alpha；
`compareImages` 只比较输出 RGB，`pixel_tolerance` 接受零 RGB 差异。
`delivery_rules.mjs` 允许色彩类型 6，而当前登记确实把 pixel_tolerance 列为可选规则。
因此这条路径可由合法配置触发，不再是上一轮的错拼模式问题。

默认 byte_equal 未被该反例绕过，不能把此发现表述成默认校验也失效。
独立测试支持的准确结论是：当前零 RGB 容差不能保证图像显示内容一致。

## 建议采用最小范围修订

下一轮只处理该像素显示语义缺口，不需要重做前三项修复或扩大实验范围。
可选择一种明确契约：

- 本轮只登记 byte_equal，拒绝 pixel_tolerance；如保留 unavailable，仍必须阻止 PASS。
- 或修复像素比较，比较包含透明度的统一表示；也可明确只接受经验证完全不透明的图片。
  透明度可能来自 alpha 或 PNG 的 tRNS 等信息，不能仅凭 RGB 通道相同认定显示相同。

无论选择哪一种，都应加入合法正对照和独立负样本：全透明、局部透明、仅 alpha 改动，
并验证修复命中显示内容差异的原因。若选择禁止该模式，就验证入口和纯规则层都拒绝
未登记模式，避免遗漏配置路径。保留默认交付、未知模式和空证据的回归检查。
