## P1：门禁接受缺失控制与缺失原始观测

将实际 raw 文件转成门禁所需的双臂结果结构，先重放得到与原报告一致的 VERIFIED_PASS。
随后只修改独立内存副本：

| 改动 | 实际门禁结果 |
| --- | --- |
| controls_result={} | VERIFIED_PASS |
| 删除一个必需控制 | VERIFIED_PASS |
| 两臂所有 raw_observation 字段置空，保留缓存裁定 | VERIFIED_PASS |
| 两臂传输记录改 exit=127、stdout 为空，保留缓存裁定 | VERIFIED_PASS |

原因：控制门禁只遍历现存 controls_result，没有必需控制清单；一致性门禁遇空 raw 就跳过，
没有检查原始证据集合、字段类型或传输结果；分类 verdict 没有从当前传输与观测重新推导。
“没有发现不一致”因此不能等同于证据已完整验证。

空 raw 反例精确指 raw_observation 字段被清空，其他缓存结构仍在；未将其夸大成文件中
任何原始字节都不存在。传输改为 127 的反例则表明当前门禁确实未重新核验执行成功。

下一版应冻结必需的探针、Arm、控制和清理证据集合；先校验存在性和完整 schema，再进行
解析、分类、重算和字段比较。缓存 verdict 只能用于对账，不能替代当前证据的裁定。
P03/P06/P08 等没有实现字段级比对的分支，也不能称为“全字段一致性验证”。

## P1：清理查询失败被报告为清理成功

本次 mock 原 DockerTransport.verified_cleanup 的全部 subprocess.run：
两次均返回 exit=1、stdout=''、stderr='daemon unavailable'。
实际没有调用 Docker。函数仍返回：

```
cleanup_verified_success = true
verified_ownership_match = true
```

代码将查询失败留下的空 queried_after 当作“已确认没有残留”，ownership 标志也默认 true。
正确行为应是清理未验证，门禁不可通过。读取失败和有效空列表必须分开，保留查询退出码、
解析状态、删除结果和前后资源集合；任何关键查询失败都不能声称已清空。

## 最终状态与退出码尚未形成统一门禁

主采集器保存 acceptance_gate_report 后，仍仅 return decision_result['exit_code']。
gate_report 的失败没有进入返回值或 rev06 输入。目前 P10–P12 未核实使整体仍为 exit 2，
但不能据此认定容器门禁已与未来完整执行器通过条件正确串联。

各层状态应分别保留，并由一个明确的总验收规则综合；容器层失败不得被另一层通过覆盖。
不要通过修改 rev06 评分规则实现这一点，应在执行器控制器层组合结果。

1. 完整实际记录保持通过正对照。
2. 任一必需控制缺失、空集合、错误类型、failed_validation 均不可通过。

5. 清理前/后查询失败、无法解析、删除失败或归属不符，均不可通过。
6. 最终总状态与退出码必须受失败门禁约束。
