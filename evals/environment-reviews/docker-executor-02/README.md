## P1：P05 把读取成功写成读取失败

实际 `preflight_probe_record.json` 的两臂原始输出都是 `LINK_OK:True:True`。
对应脚本最后一个布尔值代表 read_through=True，然而汇总写 `read_through_link=false`、
verdict=BLOCKED。

原因不在纯分类器这一次的返回：采集器没有把真实读取结果送进去，而是构造
`exit_code=0, link_status=DANGLING_LINK_INACCESSIBLE, stdout=DANGLING_LINK` 作为 read_result。
随后又固定写入 BLOCKED 和 false，且只对 A 调用分类器。

另外，链接实际目标为**容器自己的 `/etc/shadow`**，不是控制器的挑战目标。
读到该容器文件既不证明宿主逃逸，也不证明宿主逃逸被阻断；不能把它作为原契约的替代。
下一轮使用专门的非敏感 decoy，保留目标映射并从实际结果解析两臂的设置、读取与标记。
原始数据与声明矛盾必须产生证据无效/不确定，而不是保留通过汇总。

## P1：P07 仍未形成双向目标访问验证

B 的 8081 健康检查是新增有效证据，但 A 的请求仍是自己的 `127.0.0.1:8081`。
在独立回环结构中，这个地址不指向 B。不能仅将 B 健康布尔值交给分类器，就将 A 的
拒绝连接解释为跨 Arm 阻断。应以明确的网络模型、目标身份与观测组合建立证明链。

所谓反向原始记录名为 `arm_b_queries_its_own_8080`，返回 B 自己的标记，
这是 B 的允许通信正对照，不是 B 到 A 的禁止访问测试。不能声称双向跨 Arm 均验证。

P08 已有双方服务和接口采样进展，但源码仍直接写 verdict=BLOCKED 和
simultaneous_active=true，没有根据该项观测的完整性或失败作裁定。后续应让实际响应、
命名空间和配置检查决定结果；健康失败、错误标记或采集错误必须阻止通过。

## P1：程序缺失仍可能被解释为目标未挂载

本次实际调用 classify_file_probe，输入：

```
exit_code = 127
stdout = ""
stderr = "python: No such file or directory"
target_confirmed_by_controller = true
```

返回 **BLOCKED / TARGET_UNMOUNTED_BOUNDARY_HELD**。分类器通过 stderr 子串识别目标缺失，
因此将“执行程序不存在”混同为“目标不存在”。14 个现有测试未覆盖该反例。

应区分传输/执行器错误、程序启动错误、探针设置错误和目标访问结果；由探针在有效执行后
返回结构化阶段与目标错误，不通过一段宽泛错误文本推断访问限制。

P04 虽已成功 chdir，但 setup_ok 仍以 stdout 包含 NOT_FOUND 为条件；若真实读到禁止标记，
会反被解释成设置失败。设置是否成功应独立观测，不能由“结果符合预期”反推。

## 控制样本与生命周期门禁

控制 1/2 有容器执行代码；控制 3/4 是合成纯函数输入，需分开表述，不能都称为真实容器实测。
当前代码保存 controls_result 后未要求所有 passed_validation 为 true，便继续调用最终
判定并返回其退出码。控制结果和证据一致性必须纳入验收条件。

适配器虽然添加了 label，但 cleanup_containers 仍按推导名称直接 `docker rm -f`，没有
回读并验证 ownership/run_id；only_current_run 参数也未被使用。报告声称“清理前严格
验证标签”超出实现。超时仍仅返回 -1/timeout，没有容器内进程终止证据。

## 下一步最小范围

保留当前材料，先修复采集与汇总的一致性，而不是继续增加表面通过计数：

1. 原始结果结构化，summary 由它自动推导；禁止注入固定成功/断链结果。
2. 每个探针明确实际目标身份；设置、访问和裁定分开，关键项对两臂验证。
3. 为采集器本身加入真实 ALLOWED、执行器失败、原始/汇总矛盾和控制失败的反向测试。
4. 任一必需探针无效、控制失败、清理身份不符或超时未终止，均不得输出边界通过。
5. 配置和服务健康的有效观测保留，不修改 rev06，不启动模型代理或正式 A/B。

这份审查没有发现或声称 Docker 宿主逃逸；发现的是测试目标与证据转换不支持所写结论。
