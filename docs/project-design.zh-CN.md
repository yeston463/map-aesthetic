# Map Aesthetic 项目设计

Map Aesthetic 是面向现有前端地图项目的审美调整 skill。
它帮助编码代理识别地图任务、审查制图表达、修改原项目，并交付可检查的结果。
首版覆盖 Leaflet、ArcGIS Maps SDK for JavaScript、Mapbox GL JS、高德 AMap 和百度地图的适配参考。
项目交付物是 skill、参考文档、主题意图契约、校验工具与评估场景。
用户项目继续使用原有 SDK、框架、数据和原生样式配置。
首版已运行 Leaflet 本地合成演示检查；其他四个引擎属于文档覆盖。
本设计说明描述交付范围和验证方法，具体结果见[验证记录](verification.md)。

## 1. 要解决的问题

地图的视觉质量受底图、业务数据、标注、尺度、状态和应用界面共同影响。
普通前端美化能够处理面板和按钮，却未必能处理道路层级、密集点位或地图标注。
同一种视觉要求在不同引擎中可能对应原生图层、服务端样式、控制台配置或 DOM。
“把地图改成高级灰”也可能削弱路线、抹平数值差异，或者让必要地名消失。
Map Aesthetic 把这些判断整理为可复用的工作流程，并要求交付证据与能力边界。

项目希望降低三类成本：定位视觉问题的成本、选择正确修改位置的成本、复核结果的成本。
核心价值是把“看起来更好”转成与任务相关的具体改动。
例如，密集点位问题应落实到符号权重、标签优先级、尺度显隐与选中状态。
每个结论都应能回到原项目代码、真实渲染结果或明确标注的设计建议。

## 2. 目标用户与典型任务

| 用户 | 常见输入 | 期待交付 |
| --- | --- | --- |
| 前端开发者 | 代码仓库、可运行页面、SDK 信息 | 原项目内的样式与配置改动 |
| GIS 开发者 | 图层结构、业务数据、现有地图 | 制图表达与界面协同调整 |
| 产品或设计人员 | 截图、任务描述、参考图 | 视觉诊断与可实施的设计规格 |
| 维护者 | 已有主题、更新后的 SDK 或框架 | 兼容性复核与受影响状态的回归检查 |

典型任务包括视觉审计、地图重配色、业务图层突出、参考风格匹配、控件协调和主题切换修复。
收到可访问项目的实施请求时，skill 应推进代码修改及必要验证。
仅有截图时，可以完成视觉诊断与设计规格，但必须说明没有修改或验证运行代码。
参考图可以约束色调、节奏和层级；具体实现仍受数据、SDK 和服务权限限制。
输出长度与任务规模匹配，小改动无需强制生成完整审计报告。

## 3. 任务边界

审美调整默认保留数据、类别含义、分级阈值、坐标体系、业务事件和地图服务商。
底图替换、SDK 迁移、坐标转换、聚合含义变化属于需要单独说明的决策。
修改前应先判断用户原始请求是否已经包含这些工作，不能从“美化”一词自动推导。
可以改善缺失、加载和错误状态的呈现，但不能掩盖服务失败。
可以给出需要控制台操作的具体配置步骤，但不能虚构样式 ID、权限或访问凭证。
保留地图来源署名、版权信息和必须显示的服务商标识。

项目不提供跨 SDK 的运行时地图组件，不维护统一的地图实例或事件总线。
项目不提供一键迁移引擎、不承诺任意主题无损转换，也不对地图自动打“美观分”。
主题校验通过不代表制图正确、无障碍合格或商业引擎兼容。
skill 本体可以离线阅读与使用；不需要额外账号、远程推理接口或外部托管服务。
用户原项目访问地图服务时，仍遵循该项目已有的账号、权限和网络配置。
本地演示仅使用合成内容，不能冒充真实地图服务或业务环境。

## 4. 五引擎覆盖与证据等级

| 引擎 | 首版参考关注点 | 首版运行验证范围 |
| --- | --- | --- |
| Leaflet | 栅格与矢量边界、pane、路径、标注、DOM 控件 | 已验证本地合成演示中的有限子集，见运行记录 |
| ArcGIS Maps SDK for JavaScript | 图层类型、renderer、标签、MapView/SceneView、服务限制 | 文档覆盖；无商业服务实测承诺 |
| Mapbox GL JS | 样式家族、原生 paint/layout、业务图层、样式替换恢复 | 文档覆盖；无真实 token 环境实测承诺 |
| 高德 AMap | loader 与版本、原生覆盖物、可选组件、控制台样式 | 文档覆盖；无真实 key 环境实测承诺 |
| 百度地图 | 实际加载版本、兼容命名空间、样式路径、覆盖物能力 | 文档覆盖；无真实 AK 环境实测承诺 |

适配文档是代理读取的实施参考，不是已经打包完成的通用适配器程序。
运行前必须检查 lockfile、脚本地址、loader 参数、框架封装和实际初始化路径。
不能仅凭组件名称或 `BMap`、`BMapGL` 等全局命名空间确定版本。
参考中涉及版本的 API 仍应与目标项目及对应官方文档核对。
一个版本、视图类型或样式家族的结论不能自动扩展到同厂商全部产品。

验证证据采用以下分级，并记录具体版本和测试表面：

| 等级 | 可以说明什么 | 不能说明什么 |
| --- | --- | --- |
| 文档核对 | 有官方资料支持的实现路线及限制 | 用户账号可用、页面已渲染、交互已通过 |
| 本地合成验证 | 指定 fixture 内的代码和状态实际运行结果 | 商业底图、生产数据或其他引擎行为 |
| 用户项目验证 | 指定项目、版本、数据与环境中的实际观察 | 所有版本、地区、设备和服务权限 |

等级描述证据来源，不是引擎质量排名。
没有运行条件时，应继续完成可审查的代码或配置工作，并准确标记未验证部分。

## 5. 共享审美内核

共享内核首先回答“用户需要在地图上完成什么”，再决定视觉表达。
同样的点位数据，找地点、看覆盖和监测异常可能需要不同的视觉层级。
分析型地图优先保持比较关系；路线地图优先保持连续路线和必要道路信息。
运营地图需要状态变化可辨认；公共导览需要地名、地标和操作入口清楚。
深色、浅色、暖色只是实现选择，需要说明它们为什么适合当前任务。

所有审查按三个表面展开：地理背景、业务数据、应用界面。
背景提供定位参照，业务数据表达任务，界面支持操作。
应定位每个元素究竟属于瓦片图像、矢量图层、HTML 标记还是普通 DOM。
同一页面里的元素可能由不同渲染系统负责，修改方式和碰撞能力也不同。
CSS 不能被假定能独立修改瓦片里的道路、文字或 WebGL 图层。

制图调整重点包括以下维度：

- 视觉主次：必要背景保留，业务主体突出，选中状态容易定位。
- 尺度节奏：远景看分布，中景看关系，近景看细节与精确操作。
- 标注秩序：控制优先级、密度、光晕、锚点和跨系统遮挡。
- 数据语义：类别用离散编码，数量用顺序编码，有中心参照才使用发散编码。
- 空间构图：侧栏、弹窗、搜索结果和移动面板不能吞掉目标及周围上下文。
- 状态连续性：选择、过滤、主题切换和重载后，身份与含义保持稳定。

改变颜色时保留类别绑定、单位、分级阈值、缺失值和图例对应关系。
改变符号时检查点位锚点、线条接合、面透明叠加及密集区域的可读性。
降低标注密度时保留任务必需的地名和地址参照。
针对栅格底图，优先改善业务覆盖物和界面，并明确底图像素的编辑限制。

## 6. 主题契约与原生配置的关系

[主题契约](../skills/map-aesthetic/references/theme-contract.md) 用于记录视觉意图。
[JSON Schema](../skills/map-aesthetic/assets/theme.schema.json) 当前声明 `schemaVersion: "1.0"`。
它定义 `ui` 与 `cartography` 两组 token，不包含地图实例、数据加载或跨引擎调用。
此 JSON 不是 Mapbox Style JSON，也不能直接传入各厂商地图初始化函数。

`ui` 包含界面底色、文字、强调色、焦点、字体、圆角和间距单位。
`cartography` 包含地理背景、标注、类别色、顺序色、路线、站点和选中表达。
尺寸以契约定义的单位解释，不能把半径直接当直径，或把 CSS 像素直接当设备像素。
路线外描边宽度表示完整外层宽度，必须大于内层路线宽度。
尺度阈值采用视图中心附近的近似米每 CSS 像素，需结合投影和纬度映射到原生配置。
不同 SDK 的同一个 numeric zoom 不能被视为相同地面尺度。

首版提供三个起点：`quiet-analysis`、`night-operations`、`public-guide`。
预设不是强制风格，也不是适用于所有地理范围的默认尺度建议。
现有品牌系统、业务类别和数据表达优先与目标项目协调。
契约未表达某种数据编码时，保留项目原有语义，不强行套入已有字段。

语义绑定留在目标项目中，记录角色、真实图层、原生属性、单位、应用时机和恢复路径。
例如“主路线”必须映射到检查到的现有图层，不能从示例名称推断实际 layer ID。
能够直接实现时采用原生能力；近似实现时说明损失；不可实现时说明原因。
厂商专属选项继续使用原生配置，不应塞入不认识的主题字段。
这让共享设计判断可以复用，同时保留各 SDK 的能力差异。

## 7. 完整执行流程

1. **识别入口。** 判断输入是源代码、可运行页面、截图还是参考图，确认要求审计还是实施。
2. **检查项目。** 读取版本、封装、初始化、数据源、图层、当前样式和关联界面。
3. **明确任务。** 从项目推断主业务图层、用户动作、设备、数据含义和必要地理参照。
4. **记录基线。** 有运行条件时保存原始视图、视口、范围、状态及可恢复的配置。
5. **提出方向。** 用简短说明给出主次、色彩语义、符号、标注和尺度策略。
6. **检查能力。** 按请求项记录编辑表面、原生能力、近似方案、限制和证据等级。
7. **修改原项目。** 使用公开 API、已有组件和有作用域的样式，避免重写架构。
8. **处理生命周期。** 覆盖相关的加载、样式替换、主题切换、resize、卸载和重复应用。
9. **执行验收。** 校验主题结构，运行适用的项目检查，检查地图与 DOM 的实际表现。
10. **交付结果。** 提供改动、证据、限制、必要控制台步骤及恢复基线的方法。

小任务可以合并步骤，但不能省略能力判断、状态真实性和结果边界。
遇到凭证缺失时，不应停掉所有源代码审查和可独立完成的样式工作。
需要账号权限的部分，应交付精确配置项和待验证动作。
截图输入只能支持观察、设计规格和条件化实施建议。
生成概念图时，应标为设计概念，不能充当运行页面的截图。

实施时保持应用原有图层 ID、数据标识、事件关系和选择行为。
应用时机应依据引擎和应用生命周期，而不是仅依赖任意固定延迟。
Mapbox 样式替换等场景需要检查业务资源是否重建、顺序正确及监听器是否重复。
普通样式任务不应顺带更改坐标转换、服务商或业务聚合逻辑。
发现已有坐标问题时，使用项目控制点和元数据分析，不能用任意偏移改善截图。

## 8. 报告与能力状态示例

下表是虚构任务的报告格式示例，不是本仓库的测试结果。
假设任务是在不可独立编辑的栅格底图上，突出配送路线并改善移动端弹窗。

| 请求项 | 编辑表面 | 能力状态 | 处理方式 |
| --- | --- | --- | --- |
| 路线更清楚 | 原项目矢量覆盖物 | native | 调整内线与外描边，保留路线数据 |
| 道路逐级减弱 | 栅格瓦片像素 | unavailable | 说明无法逐道路修改，保持现有来源 |
| 标签减少遮挡 | 业务 HTML 标签 | approximate | 降低业务标签密度，底图内置标签保持原样 |
| 控制台专属底图样式 | 服务商配置 | unverified | 缺少可核查权限，交付待确认配置步骤 |

`native` 表示已识别到目标项目可用的直接实现路径。
`approximate` 表示只能表达部分意图，报告需要描述差异及影响。
`unavailable` 表示当前栈或表面没有所需能力；`unverified` 表示证据尚不充分。
能力状态与测试状态分开：有直接实现路径也可能尚未运行。

| 场景 | 测试状态示例 | 证据要求 |
| --- | --- | --- |
| 固定工作范围、默认状态 | passed | 具体捕获文件、范围、视口和观察 |
| 移动端选中并打开弹窗 | failed | 可复现遮挡现象及对应截图 |
| 真实服务商样式发布 | not run | 缺少权限或环境的具体原因 |

真实交付不能沿用示例状态，必须填写实际执行记录。
完整报告模板位于 [audit-report.md](../skills/map-aesthetic/assets/templates/audit-report.md)。

## 9. 视觉 QA 与真实性

QA 按任务选择最小但有代表性的矩阵，详见 [visual-qa.md](../skills/map-aesthetic/references/visual-qa.md)。
固定数据、地理范围、视口、主题、过滤条件、选择和面板状态，保证前后比较成立。
跨引擎比较使用等效范围或地面尺度，不使用相同 zoom 数字冒充相同尺度。
面板占用空间变化时，记录实际可用地图面积和相机参数。
在尺度阈值两侧检查显隐、聚合与标注过渡，避免只检查单个漂亮视角。

典型矩阵包括概览、工作、细节，以及默认、选择、弹窗、移动窄屏。
高密度、缺失值、无数据和错误状态按具体任务加入。
截图需要同时包含地图画布与 DOM，等待瓦片、标注和业务图层进入可说明的状态。
网络空闲、HTTP 成功或页面存在均不能单独证明地图已经正确显示。
无法加载时保留真实错误，不使用无关图片伪装成功底图。

交互验收覆盖实际受改动影响的平移、缩放、点击、焦点、弹窗、切换与卸载行为。
重复主题切换和组件重建有助于发现图层丢失、监听器叠加及残留 DOM。
性能检查使用代表性数据，记录设备、数据量和方法后才报告测量值。
不把视觉偏好当性能收益，也不凭静态截图宣称交互通过。

主题校验器检查结构、三个 UI 文字对比度组合及少量跨字段约束。
它不会验证感知色阶、真实文字覆盖背景、色觉差异、标注碰撞或 SDK 支持。
应把结构检查、构建检查、浏览器观察和用户项目验证分开报告。

## 10. 行为评估

[evals/cases.md](../evals/cases.md) 是供独立代理执行的行为规格，不是已运行成绩。
目前包含七类场景：Leaflet 栅格、ArcGIS 矢量专题、AMap 截图输入、百度版本歧义、
Mapbox 样式重置、坐标错位、缺少地图凭证。
每类场景给出输入、任务、预期行为和可观察失败。
执行时只向被评代理提供输入和任务，评分者再检查输出与预期。
首版实际执行了 Leaflet 栅格方案与 Mapbox 样式切换静态审查两项，均通过所需
行为检查；其余场景仍待执行。详见[独立评估记录](../evals/results/2026-11-02.md)。

评估关注是否修改正确表面、保留语义、识别版本、完成可做工作并诚实报告限制。
例如，栅格场景应拒绝假装能够逐道路换色，但仍能改善路线、点位和界面。
截图场景应交付可实施规格，并明确没有代码和运行证据。
缺凭证场景应继续可审查工作，并把真实服务验证标为未运行。
评价依据是 diff、命令结果、截图、交互复现和报告中的具体声明。
不评价代理隐藏推理，不以文案风格或单一“审美分”代替行为检查。

## 12. 维护、版本与贡献标准

项目版本与主题契约版本分别管理；`0.1.0` 项目并不意味着 `0.1` 契约。
现有主题遵循契约 `1.0`，不兼容字段变化需要升级 `schemaVersion` 并说明迁移方式。
新增语义字段必须解释用途、单位、默认策略、示例和对既有主题的影响。
适合自动检查的约束应有校验及有效失败用例；不能机械测试“美观”。
适配文档应记录核查依据，SDK 更新时优先复核受影响版本与能力。
文档核对时间、测试时间、目标 SDK 版本和运行环境应分开记录。
不要使用不带日期和条件的“最新版本”“全面支持”或“全部实测”。

新增引擎或扩充适配参考时，贡献者至少提供：

1. 实际版本识别方法、框架封装与渲染表面的区分。
2. 底图、业务图层、标签、控制件的能力表及不支持项。
3. 视觉意图到原生配置的映射、单位和生命周期说明。
4. 样式恢复、卸载、重复应用、数据语义和坐标保留策略。
5. 官方来源、已运行与未运行部分的清晰标记。
6. 能交给独立代理执行的场景，以及合法、无秘密的最小 fixture。

新增引擎不要求先建立统一运行时接口；先证明参考在具体项目中可用。
提交中不得包含用户密钥、受限样式资源或不允许再分发的地图瓦片。

## 13. 0.1 定位与后续里程碑

已形成的首版内容包括 skill 入口、共享设计参考、五引擎参考、主题契约、三套主题、
主题校验器与相关测试源码、报告模板以及七类行为评估规格。
这些文件的存在不等于其中所有行为都已执行通过。
本设计不声明已经发布 GitHub Release，也不声明真实商业服务集成已完成。

首版运行验证的范围仅为 Leaflet 本地合成演示和与其相符的检查。
它用于观察点、线、面、界面主题和部分状态，不验证真实底图样式、服务权限、
定量色带、真实标注碰撞、聚合、3D 或其他四引擎的运行行为。
已记录可复核的命令、版本、截图和限制，后续验证继续按同一证据边界维护。

后续首先在获授权的真实用户项目里验证一项具体改造，并记录反例和失效条件。
再按需求补充某个引擎、版本、样式家族的最小示例和回归场景。
只有出现多项目重复需求时，才考虑扩展主题字段或增加自动化辅助工具。
保持项目焦点：帮助代理把现有地图改得更清楚、更协调，并让结果可复核。
